Elements

Controls, labels and elements to approve

Every element Cambria CRM needs at launch, shown with real CRM content and in both themes (use the Dark button above). Each section ends with a review bar. Choose Approve or Needs changes, add a note, and save. Everyone reviewing sees each other's decisions.

  • Sections marked New are not in the design system yet. Once approved, they are added to it.
  • Sections marked Pending decision depend on a choice still open in the library (for example the rich text editor or the chart package).
  • Every section lists its accessibility checks and security risks, per the project review rule.
  • Every layout is also checked for Tab order (it follows the reading order, no forced tabindex) and for where the element usually sits in common apps, as we did for the table footer and sign-in.
  • All names, companies and amounts are sample data.
What changed in v1.2 (2026-11-04)
  • Tables: the header filter and sort menu is now a small dialog instead of an ARIA menu, approved by Chelle. It looks the same; Tab moves through it and focus stays inside until Escape or Apply.
What changed in v1.1 (2026-10-27), from the prototype review
  • Navigation: the workspace moved from the sidebar to the start of the top bar breadcrumb. New account menu with Switch workspace, Sign out of this workspace, and Sign out of all workspaces. The sidebar can collapse to icons. The workspace picker shows which workspaces you are still signed in to.
  • Buttons: secondary buttons get a new middle outline (border-strong), darker than cards and lighter than inputs, so they stand apart from Cancel without looking like a text box. Primary keeps one colour for Add and Save.
  • Selects: new Searchable option on select and multi-select. In the multi-select, picking a tag clears the search text and keeps your chosen tags.
  • Search and filters: global search shows live suggestions as you type.
  • Tables: Rows per page option (25, 50, 100). Footer reorganised: range on the left, Rows per page and page buttons on the right. The view name and custom field key moved up to the filter row.
  • Text inputs: password field with a show or hide button.
  • Toasts and tooltips: every icon-only button gets a tooltip.
  • Dialogs: Sign out of all workspaces confirmation.
  • Pipeline board: drag and drop confirmed, with the Move menu kept as the keyboard alternative.
  • Changed sections are marked Updated and still need review. These changes are not in the design system yet.

Buttons

One primary button per area, and it shares one colour whether it adds or saves; the label says which. Status colours never go on buttons, except the outlined Delete.

Updated
Variants
Sizes, icons and groups

Accessibility

  • Icon-only buttons need an aria-label ("More actions").
  • Secondary buttons use border-strong (about 2:1 against the page): darker than card borders so they stand apart from text-only buttons like Cancel, and lighter than the 3:1 input outline so a button never looks like a text box. The text label identifies the button, so WCAG does not require 3:1 on its edge.
  • Loading state sets aria-busy and keeps the label ("Saving").
  • Disabled buttons are skipped by screen readers' tab order; prefer explaining why an action is unavailable.

Security

  • Hidden or disabled buttons are not a permission check. The API must refuse the action for roles that cannot do it.
  • Primary actions disable while saving to avoid double submits (duplicate deals, double charges).

Text inputs

Labels above every field, a stronger outline for visibility, errors that say how to fix them, and a password field you can peek at.

Accessibility

  • Visible label tied to each input (for/id); required fields marked with * and the required attribute.
  • Focus is one 2px purple edge on the field (8.3:1 on white), which meets WCAG 2.2 AA; no outer outline.
  • Errors linked with aria-describedby and aria-invalid, shown in text plus icon, not colour alone.
  • Outline uses border-control (3:1).
  • Password show or hide button: its name switches between "Show password" and "Hide password", it has a tooltip, its target is 32px (WCAG 2.5.8 asks for 24px), and focus stays on the button after pressing it.
  • Sign-in order: Email, Password, Show password, Sign in, then Forgot password? below the button. Enter in either field signs in, so keyboard users rarely need to Tab to the button. The show password button stays in the Tab order: it is the only way keyboard and screen reader users can check what they typed (WCAG 2.1.1).

Security

  • Browser validation is for convenience; the API validates every field again.
  • Values are saved and shown as plain text; length limits enforced on the server.
  • Read-only and disabled fields are not trusted from the client.
  • Passwords are hidden by default and hidden again after a sign-in attempt or when leaving the screen.
  • Paste and password managers stay allowed (autocomplete="current-password" or "new-password"). Passwords are never logged, shown back or kept in app state after submit.

Accessibility

  • Select opens with Enter, Space or arrow keys, closes with Escape, and returns focus to the trigger (CDK overlay and listbox).
  • Searchable is an option on each Select and Multi-select. Use it for long or growing lists (owners, companies, tags, more than about 7 options); leave it off for short fixed lists. Without it, typing a letter jumps to the first option starting with that letter, like a native select.
  • Search boxes follow the combobox pattern: focus stays in the box, arrow keys move the highlighted option (aria-activedescendant), Enter picks it, and the number of matches is announced.
  • Multi-select: chosen tags show as chips with named remove buttons; Backspace in an empty box removes the last tag. After a pick the search text clears and the full list returns, while the list stays open for the next pick.
  • Groups use fieldset and legend; switches use role="switch".

Security

  • Option lists for owners and teams only include people in this workspace.
  • Long lists (owners, companies) are searched on the server with the same workspace and role rules, so the box never reveals names the user could not otherwise see.
  • Option text is shown as text, and the search text is sent as a parameter.
  • Visibility settings are enforced by the API and database row rules, not by hiding rows in the screen.

Search and filters

Global search in the top bar with live suggestions, active filter chips and saved views.

Updated
Global search (try "bay", "lim" or "lease")
Lead status: Hot, Warm Owner: My team Budget > $5,000

Accessibility

  • Suggestions appear after 2 characters, grouped by Contacts, Companies and Deals; arrow keys move, Enter opens, Escape closes and keeps the text.
  • Matched letters are highlighted with a tint and bold text, not colour alone.
  • Each chip's remove button names the filter it removes.
  • Result count is announced ("3 results").

Security

  • Search only returns records in the current workspace that the user's role can see (tenant filter and row rules on the server).
  • Search text is sent as a parameter, never built into SQL; rate limited per user. The box waits about 250 ms after typing stops before asking the server, and shows at most 5 suggestions per group.
  • Performance: each keystroke cancels the previous request, so old results never overwrite new ones. The server searches an indexed list that starts with the workspace, so a query only touches that workspace's records and stays fast with thousands of them.
  • Highlighting is built with text nodes, never by inserting HTML, so a record named with HTML or script cannot run.
  • Saved views store filters, not results.

Toasts and tooltips

Short confirmations with Undo, and a tooltip on every icon-only button.

Updated
Notifications Budget Custom field added by your workspace
Deal moved to Negotiation.
Notifications

Accessibility

  • Toasts announce through a live region and stay at least 6 seconds; they pause on hover and focus. Anything important also stays on the page.
  • Tooltips show on keyboard focus as well as hover and never hold the only label.
  • Rule: every button that shows only an icon has an accessible name and a tooltip with the same words. This includes Close, the sidebar toggle, the password peek, row actions, pagination, chip remove buttons, editor toolbar buttons and the Move button on deals. In this kit every icon-only button gets its tooltip from one shared script; in Angular it is one shared tooltip directive, so no button can be missed.
  • Tooltips close with Escape and stay open while the pointer is over them (WCAG 1.4.13). The Angular build uses the CDK Overlay for this.

Security

  • Toast text that includes record names is set as text, not HTML.
  • Undo calls the API within a short window; it does not just hide the change.

Accessibility

  • Active page uses aria-current; locked items say "Locked on trial" to screen readers, not just an icon.
  • Tabs: arrow keys move between tabs (try it), Tab goes into the panel.
  • A "Skip to content" link comes first in the app, then the sidebar button and the workspace.
  • Sidebar button is named "Collapse sidebar" or "Expand sidebar". When collapsed, menu items keep their names for screen readers and show a tooltip on hover and focus. Tab order is the same in both states.

  • The avatar colour is never the only cue; the workspace name is always shown as text.

Security

  • The workspace name is the first item in the top bar at every screen size, so users know which client's data they are in. The browser tab title includes it too, for example "Contacts · Acme Realty".
  • Switching workspace opens the other subdomain with its own session; tokens never cross workspaces.
  • Sign out of Acme Realty ends only that workspace session and returns to the picker. The server revokes that workspace's refresh token; hiding the screen is not enough.
  • Sign out of all workspaces ends the account session too. Recommended on shared computers. The account session also has an idle timeout.
  • The collapsed or expanded sidebar choice is a display setting saved in the browser. It holds no workspace data.
  • Hidden or locked nav items are also blocked by the API.

Accessibility

  • Density is a labelled two-option control; Compact rows (32px) stay above the 24px minimum target size.
  • Each header button names its column and state ("Filter and sort: Lead status, filtered"); the sorted column has aria-sort.
  • The header menu is a small dialog (role="dialog", the header button has aria-haspopup="dialog"), not an ARIA menu, because it holds a search box and checkboxes. Tab and Shift+Tab move through Sort, the search box, the checkboxes, Clear filter and Apply; focus stays inside until Escape or Apply, then returns to the header button. The result count is announced.
  • Every row checkbox and action button names its contact.
  • Rows per page is a labelled native select (25, 50, 100); changing it announces the new range and keeps focus on the select.
  • Footer order follows the reading order: the range on the left ("Showing 1 to 25 of 129"), then Rows per page and the page buttons together on the right. On phones the right group wraps below the range.

Security

  • The value checklist and its counts come from the server with the same workspace and role rules as the list, or they would leak values from records the user can't open.
  • Filters and sorts are sent as structured values checked against allowed fields, never built into SQL, including custom fields.
  • Filter queries are rate limited and capped; bulk actions are checked per record.
  • The server only accepts page sizes 25, 50 or 100, so a changed request cannot pull thousands of rows at once. The chosen size is saved per user and list as a display setting.
  • Every cell, including custom fields, is rendered as text.
